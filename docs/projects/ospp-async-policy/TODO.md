## 0. 使用规则

**OSPP 2026 的三条硬规则**（2026-09-14 核实于官网学生指南、FAQ 与 9 月 2 日公众号文章）：

1. 全流程滚动开放，没有固定截止日期。开发周期以项目详情为准，本课题为 **3 个月**，从中选公示起算。
2. **中选公示之前完成的开发和提交的 PR 不计入结项。** 路线 A 下，中选前只做第 0 阶段，不写实现代码。
3. **结项以 PR 合入上游为准**，无统一中期评审。F1–F4 要分批尽早开 PR，让评审和开发并行。

**状态纪律**：每项任务区分"计划 / 代码存在 / 已验证"三种状态，只有证据到位才勾选。有原型或测试文件存在，不等于整项通过。每项任务列出步骤、完成条件、证据和评审点；评审点是需要导师或维护者看一眼的地方。

**周次**从开工日计算。第 0 阶段没有周次，现在就可以做。

## 6. PR 拆分与开 PR 时机

功能分支从核对后的 `upstream/main` 建立；个人资料留在 `docs/ospp-async-policy`。每个 PR 的来源是 Fork 的功能分支，目标是上游 `main`。有依赖的后续 PR 基于前一个功能分支，评审说明中写明依赖。

| PR | 内容 | 开 PR 时机 | 合入前必须 |
|---|---|---|---|
| F1 协议基础 | 批次契约、有界队列、版本 / 协调器、CPU 测试 | 第 4 周，G1 之后 | T01–T05 证据；复用组件保留作者 |
| F2 实验 trainer | producer / consumer、CPU 闭环、生命周期 | 第 6 周，G2 之后 | F1 评审意见已处理 |
| F3 原生 backend 接入 | 并发 bridge、实际更新计数、权重同步、指标、集成测试 | 第 9 周，G3 之后 | T11–T13 证据 |
| F4 可用性与实验 | 双 GPU smoke recipe、正式功能文档、性能报告 | 第 10 周，G4 之后 | T14–T16 证据 |

若个人资料混入功能分支，从 `upstream/main` 新建干净分支后 `cherry-pick` 功能提交，不在提交后删除文档制造噪声。

## 7. 降级路径与停止规则

- **第 6 周末仍未达到 G2**：与导师商定降级范围，例如以 G1 加 bridge 设计与部分集成作为可合入的 F1 / F2，并同步修改申请书对应的产出说明。不得沉默拖延。
- **出现非有限值、持续质量退化或过高 drop**：停止该配置，收紧 lag / Q、提高同步频率，与同步路径定位差异；若需改 loss，另开算法论证，不进调度 PR。
- **上游 main 发生重大变化**，例如 PR #480 合入：一周内完成评估与变基，决策记录追加条目。
- **云机连续一周不可用**：继续 CPU 侧任务并告知导师；G2 / G3 不得以 fake 结果替代。
- **导师两周无回复**：改为公开 issue 沟通，并继续按本表推进。
