4. 汇总证据索引、已知问题、支持范围和返回原同步路径的方法；完成接手者的逐项检查。

完成条件：A01–A12 的材料可定位；官方交付没有仅以“计划完成”代替实现 / 实测的条目。PR 是否合并受外部评审影响，单独记录，不用来掩盖尚未完成的实现。

证据：候选提交、最终复现 run、检查记录与交接说明。负责角色：项目负责人及实现者。本 TODO 的准备不包含代替用户向他人发消息或创建上游 PR。

## 第一轮工作与状态维护

第一个工作日优先完成 T01 的版本 / 契约记录，建立独立功能 worktree，再为 T04 的同步饥饿问题补失败用例；同时准备 T02 / T03 的最小接口。不要一开始就增加 CLI 参数或扩到完整 Agentic 流程。

开工时可先执行这些只读核对命令；fetch 只更新远端引用，不合并当前分支：

```bash
git fetch upstream
git status --short --branch
git rev-parse upstream/main
git worktree list
```

功能分支应从核对后的上游基线建立，复用协调器或 PR 组件前逐项审查。当前资料分支继续维护本表；实际实现验证在对应功能 worktree / 云端 checkout 进行。

每次推进时记录以下内容，保持“计划、代码存在、已验证”三种状态可区分：

| 记录项 | 应填写内容 |
|---|---|
| 任务 | T 编号、负责人或负责角色、状态、实际完成日期 |
| 代码 | Fork 分支、提交 SHA、相关依赖提交 |
| 验证 | 实际运行命令、环境、run ID、结果、跳过及原因 |
| 证据 | 小型报告 / 指标文件位置；大日志与 trace 的存储位置及校验值 |
| 剩余问题 | 未通过的验收项、下一步、对排期的影响 |

资料分支中的复选框用于跟踪，不替代测试。只有 CPU 通过时停在 G1；没有真实多 GPU 证据时不勾选 G2。最终性能结论可以是提高、持平或退化，但实验过程和配置必须可复核。
